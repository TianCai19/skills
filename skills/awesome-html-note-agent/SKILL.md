# Awesome HTML Note Agent

你负责复用 `awesome-html-note-agent` 仓库里的成熟工作流，把“主题 -> HTML 笔记 -> 页面巡检 -> 迭代修改 -> 经验沉淀”串成一个完整闭环。

这个 Skill 不是单点“写一个 HTML 文件”，而是一个**总控工作流 Skill**。

## 适用场景

当用户出现以下需求时使用本 Skill：

- 把某个主题整理成交互式单文件 HTML 笔记；
- 把论文、概念、教程、代码讲解做成 HTML 笔记，而不是 Markdown；
- 对现有 HTML 笔记页面做真实浏览器巡检；
- 根据巡检建议继续迭代页面；
- 希望复用当前仓库的生成 + 巡检 + 修改方法论。

## 核心仓库约定

如果当前工作区存在以下文件，必须优先读取并遵循：

- `readme.md`
- `01-one-sentence-prompt.md`
- `02-auto-suggestions-prompt.md`
- `03-upgrade-and-summary-prompt.md`
- `experiences.md`

其中：

- `01-one-sentence-prompt.md` 负责“生成 HTML 笔记”的规范；
- `02-auto-suggestions-prompt.md` 负责“Playwright 巡检”的规范；
- `03-upgrade-and-summary-prompt.md` 负责“根据建议迭代修改”的规范；
- `experiences.md` 是经验库，若存在，必须先吸收再执行。

## 目标产物

默认目标是一个**单文件 HTML 在线笔记页面**，优先放在当前工作区根目录。

页面默认应尽量具备以下能力：

- HTML5 语义标签
- CSS Custom Properties
- BEM 命名
- CSS Grid / Flexbox
- Prism.js 代码高亮
- KaTeX auto-render 数学公式
- mark.js 全文高亮
- localStorage 批注持久化
- 自动 TOC
- 折叠推导块
- 响应式阅读体验
- 必要时加入 SVG / 可视化 / 交互模块

## 总体流程

### 模式 1：生成新 HTML 笔记

当用户给出一个主题，要求“做成 HTML 笔记”时：

1. 阅读 `readme.md`、`01-one-sentence-prompt.md`，若存在 `experiences.md` 也必须阅读。
2. 创建一个专门的「HTML 笔记生成子 agent」来完成实现，不要在主会话把生成、修改、验证混在一起。
3. 子 agent 需要：
   - 直接创建或修改 HTML 文件；
   - 完成基础自检；
   - 返回文件路径、核心功能清单、自检结果、待主会话确认事项。
4. 主会话收到结果后，打开生成页面供用户预览。

### 模式 2：对现有页面做巡检

当用户说“检查一下页面”“帮我找问题”“继续检查两轮”之类时：

1. 阅读 `02-auto-suggestions-prompt.md`。
2. 使用 Playwright 做真实浏览器巡检；优先桌面端 + 移动端双端检查。
3. 至少覆盖以下维度中的 5 类：
   - 视觉排版与信息层级；
   - 响应式布局与移动端体验；
   - 横向溢出、滚动、正文宽度；
   - 目录、折叠块、搜索、高亮、批注等交互；
   - 控制台错误、资源加载、脚本异常；
   - 内容完整度、示例质量、公式/代码/图示可读性；
   - 可访问性、键盘操作、对比度；
   - 性能、懒渲染、首屏体验。
4. 给出至少 5 条可执行建议，每条包含：问题现象、影响、修改方案、严重程度。

### 模式 3：根据建议继续迭代

当用户说“根据建议修改”“继续改”“修一下公式问题”之类时：

1. 阅读 `03-upgrade-and-summary-prompt.md` 和 `experiences.md`。
2. 根据已知建议修改 HTML 页面，优先解决高影响问题。
3. 修改后必须做基础验证：
   - 页面可正常打开；
   - 无明显控制台错误；
   - 关键交互可用；
   - 桌面端 / 移动端无明显横向溢出；
   - 本轮建议逐项处理或说明原因。
4. 修改完后再次打开页面。
5. 询问用户是否满意；若用户满意，再把可复用经验追加到 `experiences.md`。

## 强制工作方式

- **优先复用仓库现有规范**，不要脱离 `01/02/03/experiences` 自创流程。
- **优先创建子 agent** 处理生成、巡检、迭代等阶段性任务。
- **不要只停留在分析**；如果用户方向明确，应直接推进到实现、验证、打开预览。
- **优先编辑已有 HTML 文件**；只有在没有现成页面时才创建新文件。
- **每轮修改后都要验证**，尤其是公式、交互、移动端布局、控制台错误。
- **如果页面涉及真实浏览器检查，优先使用 Playwright**，不要只靠静态读代码下结论。

## 页面质量偏好（来自经验库）

默认遵循以下经验：

- 三栏布局要优先保证正文阅读区，正文宽度建议约 760–860px；
- 内容不能只停留在概念摘要，应补充公式、数值例子、图示和实践解释；
- 可视化必须服务理解，不是装饰；
- 交互模块要提供即时反馈；
- 移动端 TOC 默认收起，点击后可展开 / 自动收起；
- 代码块在移动端避免横向滚动失控；
- 每轮改动后都要复测。

## 返回格式

完成任何一轮工作后，优先按下面结构返回：

- 创建或修改的文件路径
- 已完成的核心功能 / 修改项
- 巡检或验证方式
- 巡检 / 验证结果
- 仍需用户确认的事项

## 命名建议

- 如果是新页面，文件名优先使用主题对应的 kebab-case，例如：
  - `kl-divergence-llm-note.html`
  - `flash-attention-note.html`
  - `ppo-rlhf-note.html`

## 经验沉淀规则

如果用户明确表示“满意”或“可以沉淀经验”，再把本轮可复用经验追加到 `experiences.md`。

不要在用户尚未确认满意时，提前修改经验库。

## 最终原则

你是这个仓库方法论的“总调度器”。

重点不是一次性生成某个 HTML，而是稳定复用这条链路：

**生成 -> 打开预览 -> Playwright 巡检 -> 根据建议迭代 -> 再验证 -> 用户确认 -> 经验沉淀**
